# Audit 13 — AI-Disclosure Appendix: Legal Defensibility & Honesty
Scope: `disclosure.ts` (generateDisclosureAppendix), `audit.ts` (AuditLog), `types.ts` (AuditEvent), `/sample` page, landing-page disclosure card. Assesses whether the appendix would help or hurt an expert in a real discovery/Daubert challenge.

---

## Findings

### [CRITICAL] "Verified" badge is an unsupported claim — removes plausible deniability and creates a false attestation
The landing-page mock card and sample appendix display a green "Verified" badge with no defined meaning. No code path marks any event, section, or report as verified. "Verified" in a legal context implies a sworn attestation or independent check. If produced in discovery, opposing counsel will immediately ask: who verified what, how, and when? The badge is worse than silence — it is a false representation that the system cannot back up, and it could be used to argue the expert signed off on AI accuracy beyond the content of the report itself. **Fix:** Remove "Verified" entirely. Replace with the accurate label "Generated from audit log" (already in the sample page header) or "Audit record — unreviewed by court." If a verification step is added later, it must be a signed, timestamped expert attestation captured as its own audit event.

### [CRITICAL] Disclosure statement asserts facts the system cannot guarantee: "did not originate any facts, data, or opinions"
The hardcoded `DISCLOSURE_STATEMENT` asserts that "The tool was constrained to use only the evidence the expert supplied and did not originate any facts, data, or opinions." This is a factual claim about the model's runtime behavior that the system cannot verify. LLMs can and do blend parametric knowledge with context — the system records *what was sent* but cannot prove the model produced *only* that. In a Daubert hearing, the expert will be asked to authenticate this statement under oath. If the model hallucinated even one word not derivable from the supplied evidence, this statement is perjury-adjacent. **Fix:** Reframe as a constraint-description, not a guarantee: "The system was configured to provide the model only the evidence units listed below. The expert is responsible for reviewing all AI-generated text and confirming that final content reflects only their own findings." This accurately describes the system's architectural constraint without asserting the model's inner behavior.

### [CRITICAL] Prompts are recorded in `AuditEvent.prompt` but never shown in the rendered appendix — the exact thing CLF v. Shell demands
The `DisclosureAppendix` carries `rawEvents` (including full prompts), but the `/sample` page table shows only section, model/version, and evidence sources. The rendered appendix never displays the actual system/user prompt text. Under CLF v. Shell (D. Conn. May 2026), the court ordered production of the exact prompts as Rule 26 methodology. If the rendered appendix is the disclosure artifact, it is currently incomplete for that standard. **Fix:** Add a "Prompt" column or a collapsible raw-prompt block to the appendix table. At minimum, document that the full prompt text is available on request and is contained in the underlying audit record. The appendix header should state: "Full prompt text for each AI call is retained in the audit log and available upon request."

### [HIGH] Audit log is in-memory only at runtime; database persistence exists but there is no hash-chain, no cryptographic seal, and no proof the DB record was not edited by a service-role user
`AuditLog` in `audit.ts` is an in-memory array with `Object.freeze` on individual events — a runtime guard only, gone at process restart. The Supabase migration correctly denies UPDATE/DELETE via RLS policy omission, and the comment says "(No update/delete policies => those operations are denied for all non-service roles.)" This is better than nothing, but: (1) a Supabase service-role key bypasses RLS entirely; (2) there is no hash-chain, so even if a row was replaced, nothing would detect it; (3) `audit_events.id` is generated server-side, not a content hash, so there is no integrity proof. A skilled opposing expert can argue the records could have been altered by the vendor. **Fix:** (a) Add a `prev_hash` column and compute `sha256(prev_hash || id || report_id || section_key || prompt || model || model_version || input_ids || output || created_at)` on INSERT, forming a hash chain. (b) At appendix generation time, verify the chain and record the root hash in the appendix. (c) Log or alert on any service-role access to `audit_events`. (d) Consider periodic export to a write-once store (S3 Object Lock, Worm-mode) for high-stakes cases.

### [HIGH] No human-review attestation event is captured in the audit log
The disclosure statement claims "The expert reviewed, verified, and adopted all content," but there is no `AuditEvent` for expert review/sign-off, and no `ReportSection.finalText` adoption timestamp. The appendix is therefore silent on the human-review step it asserts happened. In a Daubert challenge, an attorney will ask: "Where in your audit log does it show you reviewed this?" The answer is nowhere. **Fix:** Add a `review_attestation` event type to `ReportSectionKey` (or a parallel `AttestationEvent` type) recording: expert user ID, timestamp, and the hash of the final text they adopted. This event becomes part of the disclosure appendix, converting the assertion into a verifiable fact.

### [HIGH] Evidence-to-section mapping records IDs but the appendix renders `location` strings; if an evidence unit is later edited or deleted the appendix reconstructs incorrectly
`generateDisclosureAppendix` resolves `inputIds → location` from the live `evidence` array at generation time. If an evidence unit's `location` field was edited after drafting (or `evidenceById.get(id)` returns `undefined`, showing "(source not found)"), the appendix misrepresents what the model actually saw. The original `content` and `location` at the time of the AI call are not snapshotted in `AuditEvent`. **Fix:** Snapshot `{ id, location, contentHash }` into `AuditEvent.inputSnapshots` at call time rather than resolving live. The `content` field of evidence units can be large, so a SHA-256 hash suffices to prove what was provided without retaining the full text twice.

### [MEDIUM] "Court-ready" is an overclaim on the marketing copy and the sample page heading
"Court-ready" appears in the hero headline, Step 03 copy ("court-ready AI-Disclosure Appendix"), and the sample page metadata description. "Court-ready" implies the appendix is in a form a court will accept as satisfying disclosure obligations — a legal conclusion the vendor cannot make, and one that varies by jurisdiction and judge. If an expert uses this phrase to justify not further disclosing AI use, and a court disagrees, the marketing copy is Exhibit A in a sanctions motion. **Fix:** Replace "court-ready" with "court-facing" or "disclosure-ready." In Step 03 specifically: "Export to Word with an AI-Disclosure Appendix that records exactly how AI was used — model, version, and the evidence behind every section."

### [MEDIUM] The appendix omits what the model was NOT given — the "closed world" claim has no negative evidence
The disclosure statement says the model was given only the evidence listed. But the appendix does not list what was *excluded* — i.e., case materials that existed but were not fed to the model for a given section. In a discovery dispute, opposing counsel may argue that selective feeding of evidence to the AI constitutes a methodology choice that must be disclosed. **Fix:** Add an "Evidence not provided" note per section when the case has evidence units that were available but excluded from the input set for that section. This is architecturally straightforward: `evidence.filter(u => !e.inputIds.includes(u.id))` per entry.

### [LOW] `generatedAt` in `DisclosureAppendix` is the timestamp of document generation, not of the underlying AI calls — the distinction matters under Rule 26
The appendix `generatedAt` field will match the export timestamp, not when the AI work was done. If a report was drafted months before trial and the appendix is regenerated at export, `generatedAt` looks like a last-minute document. Each `DisclosureSectionEntry` already carries the event `timestamp`, but the top-level `generatedAt` is misleading. **Fix:** Add a `draftedAt` range (earliest and latest event timestamp) to the appendix header, and label `generatedAt` clearly as "Appendix generated" vs. "AI work performed."

### [LOW] `Object.freeze` in the in-memory AuditLog protects individual event objects but the events array itself is mutable — `events.splice` is possible inside the class
The `private readonly events` array is readonly (cannot be reassigned), but its contents can be mutated via `events.splice()` or `events.length = 0` from within `AuditLog` methods. Currently no such methods exist, but this is a latent risk if a developer adds a "clear" or "reset" convenience method. **Fix:** Consider returning `Object.freeze([...this.events])` from `all()` and `forReport()` (already done for defensive copy), and add a lint rule or comment warning against adding mutating methods.

---

## Top 3 Must-Fix

1. **[CRITICAL] Remove the "Verified" badge** — it is an unsubstantiated legal claim that cannot be authenticated and will be weaponized on cross. Replace with "Generated from audit log."

2. **[CRITICAL] Rewrite the disclosure statement** to describe architectural constraints rather than assert model behavior ("configured to provide the model only the listed evidence" not "did not originate any facts"). This is the statement the expert will authenticate under oath.

3. **[CRITICAL] Add prompt text to the rendered appendix** (or explicitly disclose its availability) to satisfy the CLF v. Shell standard. Without visible prompt disclosure, the appendix fails at the exact task it is marketed for.
